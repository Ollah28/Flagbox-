# CLAUDE.md — instructions for Claude Code in this repo

Read **HANDOFF.md** first (current status and how this setup works). Then read **SPEC.md** (what to build) and **PLAN.md** (order and acceptance criteria) before doing anything. Check **PROGRESS.md** for where we are.

## Hard rules (breaking one can disqualify the project)
1. The agent never awards, recommends awarding, or accuses. Memo wording is "warrants review".
2. No source, no flag. Claims are generated by indicator tools from templates. The model only passes `hit_id`, `severity` and a `reason_code` from a closed list; the explanation text is fixed in code (SPEC D31).
3. Every MCP tool call goes through the client-side logging wrapper (`src/flagbox/agent/logged_tools.py`).
4. Only code, never the model, calls the Filesystem server's `write_file`, and only after an approval bound to the memo's SHA-256.
5. No personal data. Drop `contactPoint`. Show supplier names only with incorporation markers (Ltd, Limited, PLC, LLP, Inc, Corporation).
6. No live tenders. Apply the ingest filter (today's date and status) to every input.
7. Never fake a run. Replay output must be labelled as a replay.

## Technical rules
- **Pin `mcp==1.30.0` (v1 API, `from mcp.server.fastmcp import FastMCP`).** Do NOT upgrade to mcp 2.x, because `langchain-mcp-adapters` 0.3.2 requires `mcp<2`.
- Ollama: `qwen3:8b` by default, `temperature=0`, `num_ctx=16384`, thinking off.
- Launch the Filesystem server with `node node_modules/@modelcontextprotocol/server-filesystem/dist/index.js ./filed`, never `npx`, because Windows needs `npx.cmd`.
- SQLite: parameterised queries only. Validate `run_id` as a UUID.
- Indicator parameters come only from `config/indicators.yaml`, never from tool arguments.
- Cap tool outputs at about 4k tokens and return totals plus `truncated`.
- Platform: Windows first. Use `pathlib`, never hard-coded `/` paths.

## How to work
1. Do one PLAN.md task at a time. Restate the task and its acceptance check before coding.
2. Write complete files. No "rest unchanged" placeholders.
3. After each task, run `uv run ruff check .`, `uv run pyright` and `uv run pytest`, and show the results. Don't move on while anything fails.
4. Explain what you wrote in plain language. The developer must be able to explain every line in a live review.
5. If reality differs from SPEC.md (an API behaves differently, a field is empty), stop, explain, propose an update to SPEC §13, and wait for an OK.
6. At the end of each task, tick PLAN.md, update PROGRESS.md, and commit with a clear message.
7. Don't add features that aren't in SPEC.md without asking.
8. New decisions go in SPEC.md §13 (the decision log). New assumptions go in §14.
